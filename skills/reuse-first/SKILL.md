# 复用优先

不要把“我能写出来”或“项目没有安装依赖”当成从零实现的理由。主动识别需求中值得复用的能力；即使用户没有点名工具，也应调查并推荐适合的库、组件、SDK、模型、服务、模板或成熟工作流程。保留用户已指定路线和已有授权，不把局部需求扩展成全项目改造。

## 识别值得调查的能力

当准备自行承担通用算法、解析、日期运算、状态协调、重试、渲染、训练机制等可复用职责，或投入明显成本重新制作已有工具/模板能完成的成果时，先做复用调查。按完整能力判断，不逐行选型，也不把一个通用机制拆成几个原生操作来规避调查。

以下例子说明判断方法，不是指定依赖清单：

- 数据工具函数：先核实项目封装、语言原生操作和成熟工具库；不能因为几行代码能写就忽略已有的边界处理。
- 日期：简单显示可由平台格式化能力覆盖；涉及解析、日期运算、时区等契约时，调查日期库，不默认用原生 Date 从零封装完整工具集。
- 视觉效果：先找现有着色器、效果组件或渲染库，确认效果与性能匹配，再决定是否需要底层 WebGL/GLSL。
- 后端、Go/Java、机器学习及 agent：同样检查标准库、框架扩展、训练/微调工具、SDK 和已有集成，避免重写通用机制。
- 非代码任务：调查现有模板、数据源、专业工具或可复用流程；核对适配成本、使用权和数据处理要求，不为简单内容编辑强行工具化。

明确的业务判断、字段映射、连接已有 API、已确认路线下的参数或文案调整，通常直接实现。若其中开始承担新的通用机制，再调查该能力。能力不因代码短而自动属于业务连接，也不因用了原生 API 就自动覆盖完整需求。

## 先查现有能力，再查外部方案

1. 检查本次相关的已有实现、调用约定、标准能力和实际依赖版本；不存在于当前文件不代表项目没有。复用仍须尊重模块边界。
2. 判断是否完整覆盖所需行为和边界。标准能力充分时直接使用；不为安装库而安装库。已经选定且适用的路线不重复比较。
3. 对尚未覆盖的可复用能力，实施前主动联网调查成熟方案，以官方文档、仓库及适用版本核实功能。调查深度与实现成本和风险匹配：局部工具函数可做短查，不需要固定数量候选或完整调研报告。
4. 核对候选的功能、环境兼容性、维护状态、引入与长期维护成本。简短说明推荐方案、实际用途、限制及必要业务适配。没有合适方案时说明依据，不凑候选、不声称穷尽市场。

明确推荐，而非仅在回答末尾附一句“也可以用库”。若成熟方案适合，建议采用并说明如何减少自行维护的代码；若不适合，说明具体取舍，不能仅以“改动少”“已经写好了”排除。

网络不可用时如实说明尚未完成外部调查，继续不依赖该选型的工作。不要把检索失败解释为没有成熟方案；未经调查不悄悄实现复杂通用替代机制。

## 选型与授权

复用已有合适能力、编写任务所需的业务规则或连接代码，可在当前任务授权内直接进行，无须为“自写代码”普遍增加一次审批。

引入新依赖、升级依赖、引入服务、切换框架，或决定自行维护较大的通用替代机制时，说明推荐路线和实质成本；没有已有授权时集中确认一次。用户已指定方案、允许安装合适依赖或明确委托选型时，按授权执行，不重复询问。付费、数据外传等操作仍须符合实际授权。

对调查后适合少量自定义实现的局部能力，说明为何没有采用候选并在任务授权内完成；不要把所有业务专用逻辑都送去联网和审批。存在显著架构、成本或行为取舍时才请用户决定。无回复不视为批准新增依赖或服务。

若本技能导致等待确认，链接本文件，说明具体待选方案及尚缺的授权；不将技能规则说成工具强制拦截。

## 实现、审查与验证

使用核实过的公开 API，保留完整需求；必要的样式、数据映射和业务连接可自定义，不在适配层重写依赖已经提供的机制。检查最终执行路径确实使用所选能力，并验证相关正常路径和边界。安装了依赖不等于完成复用。

复用审查默认只读：区分确认缺陷、重复实现的维护成本和可选建议。缺少某个库不是 bug；不因发现候选就自动替换稳定系统。

交付只说明影响决策的复用对象、必要自定义部分和验证限制。维护或评测本技能时才读取 [行为验收场景](references/behavior-checks.md)。
