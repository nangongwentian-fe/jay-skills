# 故障定位

先找可观测的失败边界，再决定修代码还是处理环境。服务控制以技能入口为准；下面的检查不授权启动、重启或停止项目。

1. 确认目标版本、入口、复现条件与期望行为。已有截图和日志是线索，记录其与当前代码/进程的关系。
2. 从实际调用链选最少观测点：页面 → 代理 → 身份/API → worker/外部服务。检查状态码、内容类型及必要的脱敏响应形状，不只看“端口开着”或 HTTP 200。
3. 对比相关配置和进程事实。只读取需要的环境键或是否设置，避免打印整份环境、连接串、Cookie 或 token。没有配置、服务未启动、权限失败和代码缺陷分别报告。
4. 用证据支持一个可检验假设，再做最小复现或修复。重复失败且没有新证据时停止盲目尝试，补充缺失观测，不通过扩大超时、隐藏错误或更换端口掩盖问题。

例如：身份接口期望 JSON 却收到 HTML，先检查前端 history fallback 和代理是否生效；不能将它解释为账号被禁用。后端直连成功只证明该路径正常，不证明浏览器同源代理与登录态也正常。

服务未启动时，告知用户所需启动入口和受阻检查，继续源码与隔离测试。用户启动后重新核对实际响应，再恢复原验收，不复用旧页面当新证据。
