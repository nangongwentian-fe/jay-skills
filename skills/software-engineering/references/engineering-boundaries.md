# 工程边界

按共同变化原因、数据所有权与真实消费者确定职责；既有公开接口优先于目录命名偏好。一个文件混合变化原因才考虑拆分，物理拆文件不等于创建共享抽象。

| 边界 | 需要确定的契约 |
| --- | --- |
| UI / HTTP / 工具入口 | 输入解析、身份上下文、结果呈现，不隐式拥有全部业务规则 |
| 应用用例 | 协调领域操作、权限、事务或工作流，清晰表达失败与重试 |
| 领域 | 业务不变量和状态转换，不依赖页面或模型自由文本 |
| 存储与外部适配 | 数据持久性、超时、幂等与外部协议，使用现有公开接口 |

这是定位职责的方法，不要求所有项目创建四层目录。小型模块可以在同文件保持清晰边界；有实际独立消费者和稳定契约再共享。跨产品复用不自动授权共享数据库、凭据或内部导入。

重构前列出受影响的调用者和要保留的行为：输入/输出格式、权限、缓存键、事件、状态恢复、错误类别。沿调用链修改，避免只改局部字段而遗留序列化、数据库或工具 schema 的旧语义。改名不能替代领域判断；数据集合碰巧相同也不能证明含义相同。
