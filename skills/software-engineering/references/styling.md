# 样式组织与复用

沿用项目现有方案。已有 Tailwind 时优先用完整、可静态检测的 utility class 及其组合表达常规样式；只有它不适合清楚、稳定表达的局部规则才放入组件 CSS/SCSS Module。不能因为 className 较长或已有 Module 文件就搬走常规样式。无 Tailwind 的项目不因此迁移。

| 需求 | 选择 |
| --- | --- |
| 布局、间距、排版、主题、常规交互状态 | 现有 utility、token、variant 或项目样式机制 |
| 复杂选择器、关键帧、局部第三方覆盖 | 项目已有组件局部样式方案，限制作用域 |
| reset、字体、主题令牌、全局基础规则 | 全局入口 |
| 不能静态枚举的运行时值 | 局部 CSS 自定义属性，必要时 inline style |

写样式前检查当前范围的重复与已有组合，优先复用基础 class、设计令牌、variant 和条件 class 工具。同一语义的样式可组合共享基础与差异变体；形似但独立变化的规则不强制抽象。样式组合足够时不新增样式库或 SCSS 抽象层。共享结构、行为与契约时才考虑组件，循环渲染不等于源代码重复。

## 重构与迁移

先标明每条规则属于组件、主题、布局、第三方还是全局。职责混杂、消费者分散或 DOM 耦合才是拆分依据，文件长度只是调查线索。

视觉不变重构先记录 class 绑定、媒体查询、关键帧和全局逃逸，再按所有权移动并更新 import。保留 specificity、加载顺序和断点行为；删除本次移动产生的孤儿规则。不要把不同组件的局部规则集中成巨型共享样式文件。项目采用 Next.js 等 CSS 分块框架且修改入口或顺序时，检查生产产物，不能只看开发环境。

新增依赖、构建机制或扩大迁移超出已有授权时，提出具体范围、收益、风险与验证方式后确认；已有授权不重复询问，不因偏好主动更换技术栈。

## 验证

按影响选择真实页面的断点、交互状态、主题和动效检查，保留项目门禁。关注全局泄漏、被裁切内容、焦点可见性和覆盖顺序。纯样式修改不要求无关逻辑测试；涉及构建入口或 CSS 顺序时验证生产构建。不为本次任务擅自引入 lint、截图或样式依赖。
