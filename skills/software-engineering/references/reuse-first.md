# 复用优先

"我能写出来"或"项目没装这个依赖"都不是从零实现的理由。准备自己承担一项通用能力时，先确认已有实现和成熟方案是否已经覆盖；即使用户没点名工具，也主动调查并推荐合适的库、组件、SDK 或框架扩展。用户已指定的路线和已有授权保持不变，局部需求不扩成全项目改造。

## 什么时候调查

当你准备自写通用算法、解析、日期运算、状态协调、重试、渲染、国际化、训练机制等可复用职责时，先做复用调查。按完整能力判断，而不是逐行判断：把一个通用机制拆成几个原生操作（useState + localStorage + 对象索引）仍然是在自写这个机制。

判断方法举例（不是依赖清单）：

- 数据工具函数：先核实项目封装、语言原生操作和成熟工具库；几行能写完不代表边界处理也覆盖了。
- 日期：只做显示时用平台格式化能力；涉及解析、运算、时区时调查日期库。
- 视觉效果：先找现有着色器、效果组件或渲染库，确认效果和性能匹配，再决定是否需要底层 WebGL/GLSL。
- 后端、Go/Java、机器学习和 Agent：同样先查标准库、框架扩展、训练/微调工具、SDK 和已有集成。

明确的业务判断、字段映射、连接已有 API、已定路线下的参数或文案调整，直接实现即可。其中一旦开始承担新的通用机制，再调查这部分。

## 先查现有能力，再查外部方案

1. 检查相关的已有实现、调用约定、标准能力和实际依赖版本。当前文件里没有不代表项目里没有；复用时仍须尊重模块边界。
2. 判断是否完整覆盖所需行为和边界。标准能力足够就直接用，不为装库而装库；已选定且适用的路线不重复比较。
3. 对仍未覆盖的能力，实施前联网调查成熟方案，用官方文档、仓库和适用版本核实功能。调查深度与实现成本和风险匹配：局部工具函数做短查即可，不需要固定数量的候选或调研报告。
4. 核对候选的功能、环境兼容性、维护状态和长期维护成本，简短说明推荐方案、用途、限制和必要的业务适配。没有合适方案时说明依据，不凑候选。

推荐要明确，不能只在回答末尾附一句"也可以用库"。如果不采用成熟方案，说明具体取舍；"改动少""已经写好了"不是充分理由。

网络不可用时，如实说明外部调查未完成，继续不依赖选型的工作。检索失败不等于没有成熟方案，也不能因此悄悄自写复杂的通用替代机制。

## 选型与授权

复用已有能力、编写业务规则或连接代码，在当前任务授权内直接做，不需要额外审批。

引入或升级依赖、引入服务、切换框架，或决定自己维护较大的通用替代机制时，说明推荐路线和实际成本；没有已有授权就集中确认一次。用户已指定方案、允许安装合适依赖或明确委托选型时，按授权执行，不重复询问。用户没回复不算批准；付费、数据外传等仍须符合实际授权。

调查后适合少量自定义实现的局部能力，说明为什么没用候选，然后在任务授权内完成。只有存在明显的架构、成本或行为取舍时才请用户决定。

## 实现、审查与验证

使用核实过的公开 API。样式、数据映射和业务连接可以自定义，但不在适配层重写依赖已经提供的机制。检查最终执行路径确实用上了所选能力，并验证正常路径和边界；装了依赖不等于完成了复用。

复用审查默认只读，区分确认缺陷、重复实现的维护成本和可选建议。缺少某个库不是 bug，发现候选也不自动替换稳定的系统。

交付只说明影响决策的复用对象、必要的自定义部分和验证限制。评测场景见 [复用评测](../evals/reuse-first-scenarios.md)，仅在维护本技能时读取。
