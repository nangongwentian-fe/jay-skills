# 软件工程

围绕用户任务与可观察行为组织实现。先核实实际技术栈、调用链和现有能力，再选择最小充分改动；不按目录数量、文件长度或抽象层数判断质量。用户当前明确要求优先于本技能的默认偏好。

## 先确认工作模式

- **开发、修复或重构**：完成已授权的代码、相关文档与必要验证；不将局部修改扩为全仓迁移。
- **源码 Review**：默认只读，追踪调用方与可达路径；报告证据，不顺便修复、安装依赖或更新快照。
- **UI Review**：实际页面检查视觉、交互与可访问性；源码解释根因，不能替代页面验收。
- **故障解释或方案讨论**：先给出已验证事实、推断和建议；不把“为什么”转换为改代码或启动服务的授权。
- **跨层任务**：追踪本次涉及的边界，合并同根问题；不因“全栈”遍历所有模块。

读取适用项目指令、目标模块说明、直接调用方及相邻测试；从依赖和脚本确认框架版本与检查入口。小型文案或间距修改只读必要上下文，不预读全部架构材料。

## 项目运行由用户控制

这是用户的长期工作偏好，适用于前端、后端、数据库、worker、Agent 服务与本地网关。

- 发现项目或所需服务未启动时，告诉用户缺少哪项服务、影响哪部分验证，并根据仓库实际脚本给出启动方式，由用户启动。在面向用户的回复中直接说明需要其启动什么，不能只把这条要求写进内部报告；若入口是不可运行的桩或缺失，说明需要用户提供或启动真实环境，不把桩命令当成有效启动指令。不要自行执行 dev/start/serve、watch、preview、Compose up，也不要以“临时验收”“健康检查”或后台任务为理由启动项目。
- 不擅自重启已有服务、杀占端口的进程、换端口或单独启动子服务绕过统一入口。需要重启才能生效时说明原因，交给用户处理。
- 普通“修复并验证”不等于授权启动项目。只有用户明确要求本次由 Agent 启动或管理服务时，才按该次范围执行；这不取消后续任务的默认偏好。
- 可以只读检查目标端口、进程、响应状态与内容类型、相关配置；不输出凭据。继续不依赖服务的实现、lint、类型检查、构建和测试，不把整个任务停在环境缺口上。
- 一次性检查不受上述常驻服务限制，但先核对脚本是否隐式启动项目、真实数据库或容器。纯进程内模拟、隔离临时数据的单元测试可正常执行；需要项目服务的集成/E2E 检查等待用户启动。
- 用户要求“停止你启动的”时，只终止有本次启动记录可证明归属的进程及子进程，再验证退出或端口释放。不能因为进程使用了相关端口就推定属于自己。

## 实现与交付

先检查已有实现、标准能力、框架机制和可用专项技能。需要新的可复用机制时按可用的 `reuse-first` 调查；业务连接或已选方案不重复选型。不要把参考项目的目录、库或框架当作当前项目模板。

迁移同步更新消费者、导入导出、契约和相关文档；保留用户数据、状态身份、错误语义与任务外的工作。验证用户可观察行为，按影响执行必要检查和项目强制门禁；低风险局部改动不新增只复述实现的测试。

浏览器连接由可用的 `chrome-browser-validation` 负责；前端参考负责检查内容。Git、部署、清理分别沿用实际可用的独立技能和已有授权，不复制其流程。本技能不要求为普通任务委派子 Agent，也不额外授权外部写入、安装依赖或发布。

交付先说明最终效果及影响使用的剩余缺口，再列验证证据。区分静态推断、隔离测试、真实集成和视觉验收；未启动的服务、未运行的模型和未执行的测试明确写未验证，不以构建成功代替功能完成。
