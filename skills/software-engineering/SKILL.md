# 软件工程

以用户任务和可观察行为为中心：先核实实际技术栈、调用链和已有能力，再做最小充分的改动。质量看行为是否正确、边界是否清楚，不看目录数量、文件长度或抽象层数。用户当次的明确要求优先于本技能的默认做法。

## 先确认工作模式

不同模式的授权不同，认错模式是越权最常见的原因。

| 模式 | 做什么 | 边界 |
| --- | --- | --- |
| 开发、修复、重构 | 完成授权的代码、相关文档和必要验证 | 局部需求不扩成全仓迁移 |
| 源码 Review | 追踪调用方和可达路径，报告证据 | 默认只读：不顺手修复、装依赖或更新快照 |
| UI Review | 在实际页面检查视觉、交互和可访问性 | 源码只用来解释根因，不能替代页面验收 |
| 故障解释、方案讨论 | 给出已验证事实、推断和建议 | 问"为什么"不等于授权改代码或启动服务 |
| 跨层任务 | 追踪本次涉及的边界，合并同根问题 | 不因为"全栈"就遍历所有模块 |

上下文按改动大小读取：项目指令、目标模块、直接调用方和相邻测试，并从依赖和脚本确认框架版本与检查命令。只改一处文案或间距时，读必要部分即可。

## 服务由用户启动

用户可能在运行自己的实例、连着真实数据或占用特定端口，Agent 自行启停会破坏这些状态。

- 需要的服务没启动时，在给用户的回复里写明缺哪项服务、影响哪些验证，以及仓库中实际的启动命令；入口缺失或只是桩时，说明需要真实环境。然后继续做不依赖服务的实现、lint、类型检查、构建和隔离测试。
- 不执行 dev/start/serve/watch/preview/compose up，不重启服务、杀端口进程或换端口。"修复并验证"不算启动授权；用户明确要求本次由你启动时，只在本次范围内管理。
- 可以只读检查端口、进程、响应和配置（不输出凭据）。运行一次性脚本前，先确认它不会隐式拉起服务、真实数据库或容器。
- 用户要求停掉你启动的服务时，只终止能证明是本次启动的进程。

## 实现与交付

- 动手前先找已有实现、标准库、框架机制和可用的专项技能。准备自己承担通用机制（解析、日期运算、重试、状态协调、渲染等）或新增依赖时，按[复用优先](references/reuse-first.md)调查；业务规则、字段映射和已选方案直接实现。参考项目的目录和库不是当前项目的模板。
- 迁移时同步更新消费者、导入导出、契约和文档，保留用户数据、状态身份、错误语义和任务外的修改。
- 验证用户可观察的行为，并执行项目强制门禁。低风险的局部改动不必新增只复述实现的测试。
- 浏览器连接交给 `chrome-browser-validation`，Git 提交和部署交给对应的独立技能；本技能只规定检查什么，不复制它们的流程。普通任务不需要委派子 Agent，本技能也不额外授权安装依赖、外部写入或发布。

交付时先说最终效果和影响使用的缺口，再列验证证据，并标明每项证据属于静态推断、隔离测试、真实集成还是视觉验收。没启动的服务、没跑的测试写"未验证"；构建成功不等于功能完成。
