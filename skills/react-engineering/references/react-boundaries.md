# 组件与状态

## 组件边界

按业务含义、变化原因和交互所有权提取组件。共享 UI 保持业务无关，业务组件可以直接消费业务 Hook；无需一律划分 container/presentational 两层。相同外观不代表相同契约，两个独立变化的表单不必合成一个多模式万能表单。

组合用 children、具名 slot 或清楚的子组件表达；只有多个子组件确实需要共享协调状态时才考虑 Context。不要为减少 props 数量隐式隐藏依赖。

组件定义放在模块作用域，避免在父组件渲染中定义并作为组件挂载而改变身份。普通 render 回调与组件类型有区别，表格 Cell/render props 不因返回 JSX 就一律禁止；检查消费方的实际调用契约，若作为组件类型挂载，同样受组件身份规则约束。提取时核对 key、条件渲染、树位置和组件类型变化是否改变状态生命周期。

## Hook 边界

Hook 表达一个明确的有状态能力或外部同步职责，例如 useOrderFilters 或 useConnectionStatus。复用不是唯一理由，单个消费者也可因职责清晰而提取；没有 React Hook 调用的纯转换通常用普通函数命名，不加 use 前缀。

不要把整个页面机械搬进巨型 Hook，也不要用 useMount、useEffectOnce 等包装隐藏依赖。遵守已安装 React 版本的 Hooks 规则及 lint；为控制执行频次而省略响应式依赖会制造闭包错误。每次调用自定义 Hook 拥有独立状态；抽到同一个 Hook 不会自动让两个组件共享状态。

不通过 Effect 保存能由当前 props/state 算出的筛选结果或总数；在渲染时计算，确有成本依据再使用 memoization。用户操作引发的提交放在事件处理路径，Effect 用于外部系统同步。不要为“工程化”普遍增加 useMemo/useCallback/memo。

订阅、定时器及网络同步需要匹配的清理。异步场景保持已有取消/忽略过期结果机制，防止旧请求覆盖新状态；已有查询库负责的逻辑不再手写一套。开发期重复 setup/cleanup 应当正确，不用一次性 ref 绕过清理问题。

## 状态所有权

确定 React 自有状态前，核实框架及已安装组件库的公开 API、当前版本和生命周期契约。库能完整管理的开关、选择与关闭生命周期不再平行维护；需要 URL、兄弟组件、业务流程或异步结果协调时，保留由明确所有者控制的状态，不为减少 useState 强行改成非受控。不可只因库有一个同名 API 就假定覆盖需求。

实体选择保存稳定业务 ID，从权威数据和当前语言派生内容；可排序、过滤或翻译的数据不以数组索引或译文对象作为持久选择身份。若库支持类型化 trigger payload，可复用该公开契约而不另存一份选择状态；迁移时核对关闭动画期间内容、重新打开、重置时机及触发器焦点恢复。

| 状态含义                               | 默认所有者                               |
| -------------------------------------- | ---------------------------------------- |
| 单个交互的展开、输入或选择             | 使用者附近；需要协调时提升到最近共同祖先 |
| 可分享、刷新和前进后退恢复的筛选或分页 | 现有 URL/路由状态机制                    |
| 服务端结果及请求状态                   | 现有数据层缓存或框架机制                 |
| 表单草稿、校验和提交状态               | 当前表单或已有表单方案                   |
| 多处长期共享的应用状态                 | 已有 Context/store；先确认确需全局共享   |
| 可推导的值                             | 从权威输入计算，不另存一份同步状态       |

将状态下移前检查协调消费者，上移前检查其生命周期。重构不应意外清空草稿、丢失焦点或把实例局部状态变成全局状态。Server Components 项目遵循框架边界，不将服务端模块或敏感配置导入客户端，也不因一个交互就把整个页面标为客户端组件。
