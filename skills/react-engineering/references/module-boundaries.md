# 模块与依赖

## 目录服从所有权

先检查实际消费者、共同变化原因和依赖方向，再决定沿用或调整项目的 pages、routes、modules 或 features；名称一致不能证明归属合理。业务功能变复杂时，把共同变化的 UI、请求、类型和逻辑放在一起；只创建实际需要的目录。共享目录存放跨业务稳定契约，不作为难以归类代码的收纳箱。页面专属区块、配图和数据靠近页面；公共导航与页脚归布局，通用控件独立归属。混合这些职责时按实际归属迁移，不只在原目录继续拆文件。具体目录形状服从框架和消费者，不把单页项目的 app/pages/home/components 结构定为通用模板。

以下只是已有业务分组需求时的例子，不是初始化模板：

```text
src/
  app/                      # 路由与跨功能组合，框架项目沿用框架目录
  features/
    orders/
      api/get-orders.ts     # 请求、查询配置、业务查询 Hook 可同文件
      components/order-list.tsx
      components/order-filters.tsx
  components/ui/            # 已有共享 UI
  lib/api-client.ts         # 已有请求基础设施
```

命名、单复数、文件后缀和别名沿用仓库约定。样式、测试和类型通常靠近使用处；没有复用需求的类型不必独立成文件。只因未来可能有第二个应用，不提取 workspace package。

## 依赖方向

默认让应用组合层依赖业务模块，业务模块依赖共享能力；共享层不反向依赖某个页面。两个业务模块需要合作时，先考虑在页面/路由组合并通过 props 或业务接口传递数据。确有共同领域概念时再确定领域归属，避免通过全局 store 或事件总线掩盖循环依赖。

禁止跨 feature 导入是可选架构策略，不是 React 规则。已有合法公共 API 和清晰单向依赖时，保留它，不为符合示例进行全仓改造。跨模块消费公开契约，避免深挖对方内部实现；迁移时检查运行时循环及服务端/客户端边界。

保留已有 package exports 和必要聚合入口。不要给每层目录自动生成 index.ts，也不要以未经测量的 tree-shaking 猜测删除所有 barrel；内部精确导入与稳定公共入口可以并存。

## 数据层归属

先复用框架 loader、服务端数据能力或已有查询库。请求函数负责传输；查询配置负责缓存键、查询参数及失效契约；Hook 连接 React 消费端。它们职责可分开，文件不必分开。业务查询 Hook 可以放 api 目录，不强制集中到全局 hooks。

缓存键覆盖影响结果的参数，复用已有查询配置，避免页面各自制造相同数据的缓存和 loading 状态。共享 API 已有统一目录时可以保持；不要为了 feature 风格复制请求封装。新增数据层依赖需要实际需求和授权，不因参考项目使用某库而安装。
