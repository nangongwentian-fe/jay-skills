# 行为评估参考

## 失败模式

“遵循现有约定”和“最小改动”可能被误读为无条件保留目录与状态结构，即使用户要求工程重构，也只补局部类型约束。评估要证明 agent 能区分行为兼容与结构选择，同时避免把一次重构的目录或组件库 API 变成固定模板。

## 场景与判定

| 场景                                                             | 验收依据                                                                               |
| ---------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 页面专属内容散落公共目录，布局包含页面业务，用户要求整体工程整理 | 实际产物按消费者与依赖组织，修正问题涉及的边界；不能只改命名或类型并默认保留不合理归属 |
| 已安装弹窗库覆盖选择与关闭，手写状态重复维护相同能力             | 核实公开契约后复用；选择身份稳定，选择、关闭、重开与焦点行为保持                       |
| 职责集中、依赖清晰的小页面                                       | 允许保留，并说明证据；不预建 feature/store 或通用 Hook                                 |
| 用户明确只修局部行为                                             | 完成局部任务，结构观察单独报告，不擅自扩大迁移                                         |
| 弹窗与 URL、兄弟组件或异步流程协调                               | 保留必要的受控状态，明确唯一所有者；不机械移除 useState                                |

## 执行方式

使用不继承聊天历史的子 agent，提供现实用户任务、技能入口及最少原始材料，不提供本页验收答案或此前结论。评估者可以按技能路由读取参考；不把预期方案写入任务提示。重构在独占临时目录进行，复用已有依赖，不改主项目或技能。对照输入检查代码与依赖方向，运行类型检查；交互场景实际操作选择、关闭、重开及必要状态保持，不能用初始静态渲染冒充交互验证。

分开报告结构校验、决策判断、实际代码运行和未验证内容。失败时根据观察修正规则，使用新的无历史 agent 复测相关场景；最多两轮修正，仍失败则明确保留未通过项。记录精简结果到现有技能决策记录，清理临时材料，不把测试脚手架变为产品代码。
