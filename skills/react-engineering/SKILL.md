# React 工程组织

以 Bulletproof React 的工程组织经验为参考，以 React 官方语义约束正确性。目标是让职责、依赖和变化范围清楚；目录数量、文件长度和抽象层数不是质量指标。

## 先确定实际边界

读取目标代码、直接调用方、项目指令与相关决策；从依赖和配置确认 React、路由、构建及数据层的实际版本。区分客户端应用与包含 Server Components 的框架项目，不把 Vite 示例的结构直接套到框架路由中。

先找已有业务模块、组件、请求封装和状态约定，复用适用能力。先验证现有组织的职责、消费者和依赖方向；一致不等于合理，保留结构需要证据，不能作为默认前提。发现职责混杂、共享层反向依赖页面、重复状态或所有者错误时，在授权范围内一起修正；明确的局部任务不扩成无关全仓迁移或技术栈更换。分析请求给出建议，实施请求完成授权范围内的修改；本技能不授权提交、发布或安装依赖。

## 按职责选择动作

| 观察到的事实                                         | 默认动作                                               |
| ---------------------------------------------------- | ------------------------------------------------------ |
| 小页面职责集中，现有 pages/components 等目录足够清晰 | 沿用现状，不预建 features、stores 或 packages          |
| 一个业务功能已有多种共同变化的文件                   | 在项目现有业务目录内聚，按需考虑 feature 边界          |
| 代码只有一个业务消费者                               | 靠近消费者保留，可在同文件内定义私有组件或函数         |
| 多个消费者共享稳定的业务契约                         | 提取到能覆盖这些消费者的最小共享范围                   |
| JSX 包含可独立描述的交互、状态或变化职责             | 考虑组件边界；先说明拆分解决什么问题                   |
| 有明确职责的有状态逻辑或外部同步逻辑                 | 考虑自定义 Hook；纯计算使用普通函数                    |
| 多个布尔参数形成互斥或矛盾组合                       | 按实际状态用联合类型或组件组合，不自动引入通用配置引擎 |

组件提取与文件拆分是两个决定。不因为超过某行数、props 数量或 JSX 深度就强制拆分，也不要求每个组件配一个 Hook。提取后若只是把耦合藏进返回大量字段的 usePageModel，继续检查职责和状态归属。

涉及目录迁移、跨模块依赖或共享层设计时，读 [模块与依赖](references/module-boundaries.md)。涉及 Hook、状态或交互重构时，读 [组件与状态](references/react-boundaries.md)。需要追溯依据或判断上游建议的适用条件时，读 [来源与取舍](references/sources.md)。无需每次加载全部参考。

## 改动与验证

区分行为兼容要求与内部结构选择：保护用户需要的行为，不默认冻结目录、组件树或状态实现。选择最小充分改动，以完整解决已识别的问题为准，不以移动文件最少为准；先确认职责和状态所有者，再调整组织。移动代码时同步修复导入、必要公开导出、测试 mock、路径配置和当前文档。保留原有 DOM 语义、焦点、键盘行为、状态身份、重置时机及异步失败处理。

沿用已有 lint、类型和测试能力；适用时将明确依赖边界放入现有 lint 配置，不为目录偏好引入新工具。验证可观察行为，尤其是状态保留/重置、查询参数、异步乱序和组件卸载；不用固定私有组件树的测试证明拆分正确。遵守项目强制门禁，交互或视觉受影响时执行相应浏览器验证。

交付说明具体边界为何改变、行为如何验证及未覆盖的风险。保持现状时说明现有职责与依赖为何合理；不要为展示规范而增加目录或抽象。

修改或评估本技能时，读 [行为评估](references/behavior-checks.md)，用隔离任务检验决策及实际产物；日常 React 开发无需加载该参考。
