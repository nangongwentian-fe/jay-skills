# Post-Task Learning Review

Capture knowledge that would materially change future work. Apply this when the task produces a verified, reusable discovery or the user requests learning maintenance; ordinary task completion alone is not a reason to create notes.

## Choose the owner

| Knowledge | Destination |
| --- | --- |
| Project decisions, contracts or operational procedures | Existing project docs or the project's decision-record system |
| Reusable workflow with an existing skill | That skill's maintained source |
| Stable cross-project preference or verified environment lesson | The active authoritative memory system, under its write protocol |
| External technical material | The user's requested knowledge destination, under its write protocol |

Search the relevant owner before adding. Correct or consolidate existing guidance when it serves the same purpose. Avoid diaries, raw logs, ordinary coding advice, speculative lessons and one-off preferences. Create a new skill only for a reusable workflow with a clear trigger and no suitable existing owner.

## Authority and scope

- Skill activation grants no write permission. Follow the current task, project rules, filesystem permissions and external-action boundaries.
- Maintain local project docs or skill sources when necessary to complete the authorized task. Do not make optional unrelated maintenance a prerequisite for finishing it.
- For memory, first identify the active authority and its protocol. If it requires preview and confirmation, show the proposed content, scope and destination and wait. Do not bypass that requirement with an Inbox, local cache, update note or a second memory store.
- Do not infer a permanent preference from one action, or save secrets and sensitive credentials.
- Editing a skill does not authorize committing, pushing, publishing or installing it. Reuse explicit authorization when the user has already granted those actions.

## Complete the maintenance

Preserve project-specific decision-record requirements, including lifecycle, translations, archives and required checks. Do not replace them with this generic workflow or import a personal institution into unrelated projects.

Use the active skill-creation guidance for substantive skill changes and validate changed artifacts proportionally. Fix authorized, in-scope issues before handoff; otherwise state the smallest unresolved decision.

Report actual maintenance and meaningful limitations briefly. If nothing qualifies, no maintenance or special final-response section is required unless the user asked for a learning report.
